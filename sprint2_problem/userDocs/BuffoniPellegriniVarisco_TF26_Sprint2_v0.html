TF26 - Sprint2

Goal Sprint2: Progettare e realizzare l'attore cargorobot e integrarlo con l'ambiente virtuale RobotSmart26 per eseguire la missione autonoma di trasferimento container (IOPort -> slot 5 -> slot assegnato -> HOME). Modellare il componente marker per la sincronizzazione del processo di marcatura nello slot 5.

Introduction

A Maritime Cargo shipping company (from now on, simply company) intends to automate the operations of load of containers in the ship’s cargo hold (or simply hold). To this end, the company plans to employ a Differential Drive Robot (from now, called cargorobot).

The hold is a rectangular, flat area with an Input/Output port (IOPort). The area provides 4 slots to store the containers and a slot named slot5.

In the picture above:

  • The slots1-4 depict the hold areas reserved to store one container each,
  • The slot5 depicts an area, where the cargorobot must temporarily store a container, before to place it in one of the slots1-4. During temporary storage, a ‘marker’ device labels the container with an identification barcode and signals when this marking activity is completed.
  • The IOPort is a device with a pushbutton and a display. The pushbutton is pressed by the customer in order to to send a request to load a container on the cargo. The display is used to show the answer to the request and to show the current state of the hold.
  • The sensor associated to the IOPort is a device (a sonar) used to detect the presence of a container, when it measures a distance D, such that D < DFREE/2, during a reasonable time (e.g. 3 secs).

Requirements

The company asks us to build service named cargoservice that should work as follows.

The cargoservice is able to receive a request to load a container sent by some customer by using the pushbutton of the IOPort.

  • It sends the answer retrylater, if the IOPort is currently occupied by a container or if the system is Out of service
  • It rejects the request when the hold is already full, i.e. the slots1-4 are already occupied.
  • Otherwise, it considers the system as engaged, detects a free slot and returns as answer the name of such a reserved slot. While engaged, the system must blink a Led.

When the request to load is accepted, the customer must move the container in the sensor area within prefixed amount of time (e.g. 30 secs), otherwise the systems becomes disengaged. Then, the cargoservice uses the cargorobot to move the container from the IOPort to the slot5 (for marking the container) and then to the reserved slot.

The service must also show on the display on the IOPort:

  • the current state of the hold
  • the message ‘Service working’, when it is all is going well
  • the message ‘Out of service’ if the sonar sensor measures a distance D > DFREE for at least 3 secs (perhaps a failure of the sonar).

Problem analysis

Il ruolo di cargorobot come componente intermedio

Come evidenziato nell'analisi dei requisiti dello Sprint 0, RobotSmart26 è il servizio esterno individuato per governare il robot a guida differenziale (DDR), in quanto riduce l'abstraction gap calcolando autonomamente il path-planning a partire da coordinate cartesiane. Tuttavia, RobotSmart26 è un componente infrastrutturale agnostico rispetto al dominio applicativo: non conosce i concetti di stiva, container, slot riservato, marcatura barcode o fasi di carico.

  • Separazione delle responsabilità (SRP): Far interagire direttamente cargoservice con RobotSmart26 sovraccaricherebbe l'orchestratore di dettagli operativi legati alle tratte e creerebbe un accoppiamento tecnologico stringente verso il simulatore.
  • cargorobot come attore intermediario: Si introduce cargorobot come entità autonoma dotata di ciclo di vita proprio (QActor). Riceve da cargoservice l'ordine di trasporto ad alto livello (transportContainer(SLOT, X, Y)), coordina la sequenza di tappe e traduce la missione in chiamate verso il servizio robot.

Canale di Comunicazione verso RobotSmart26

Analizzando le interfacce esposte da RobotSmart26:

  1. MQTT: Richiede la presenza e la manutenzione di un broker aggiuntivo (come Mosquitto), oltre a dover gestire manualmente l'impacchettamento e la correlazione asincrona dei messaggi su topic distinti (robotsmart26in e robotsmart26in_out).
  2. CoAP: Orientato prevalentemente all'osservabilità delle risorse (es. stato di robotmnemo). Il suo uso per il comando richiederebbe la riscrittura a mano del layer di richiesta/risposta.
  3. ExternalQActor su TCP (Scelta di Progetto): Poiché RobotSmart26 è esso stesso sviluppato mediante l'infrastruttura QAk, è possibile referenziarlo direttamente come ExternalQActor su un contesto remoto (ctxrobotsmart). L'infrastruttura QAk gestisce in modo trasparente e nativo la serializzazione dei messaggi e il socket TCP, senza intermediari o librerie esterne.

Livello di astrazione dei comandi di movimento

Il componente software RobotSmart26 non espone una singola modalità di pilotaggio, bensì diversi livelli di astrazione per il controllo della navigazione del DDR. Nell'ottica di ridurre l'abstraction gap senza introdurre complessità non richieste dal committente, è necessario analizzare comparativamente ciascuna alternativa:

  1. Comandi elementari di navigazione: step e move
    • Definizione e Semantica: Costituiscono il livello di interazione a più basso livello esposto dal servizio. Comprendono primitive atomiche come il singolo passo in avanti calibrato su un tempo prestabilito (step(TIME)) con relativa risposta di esito (stepdone(V) / stepfailed(DURATION, CAUSE)), e comandi asincroni di rotazione o arresto inviati via dispatch (move(M) con M in {l, r, a, d, h}).
    • Contesto d'uso ideale: Questa modalità è concepita per problemi di esplorazione euristica o mappatura dinamica, ovvero per scenari in cui lo spazio di manovra non è noto a priori e il robot deve procedere per tentativi analizzando l'ambiente passo dopo passo (ad esempio costeggiando un perimetro ignoto).
    • Valutazione critica per il progetto: Nel nostro scenario, l'ambiente della stiva è rettangolare, statico e con coordinate ben definite note a priori fin dalla fase di analisi (HOME, IOPort, slot5, slot1..4). Optare per questo approccio costringerebbe l'attore cargorobot a farsi carico della gestione della bussola interna, della verifica dell'orientamento, del conteggio dei singoli passi e della ri-pianificazione manuale in caso di scostamento. Ciò reintrodurrebbe all'interno dell'applicazione una complessità algoritmica di basso livello che è già stata risolta a monte dal componente RobotSmart26, annullando di fatto il beneficio della sua adozione.
  2. Pianificazione ed esecuzione disaccoppiate: buildPlan seguito da doplan
    • Definizione e Semantica: Questo livello separa nettamente la fase di calcolo del tragitto da quella di attuazione dei movimenti. L'invio della richiesta buildPlan(PX, PY, TX, TY) istruisce il servizio a elaborare una sequenza formale di passi e rotazioni ottimali per passare dalle coordinate di partenza (PX, PY) a quelle di destinazione (TX, TY), restituendo il piano nella reply buildPlanDone(PLAN). Successivamente, il chiamante inoltra tale piano tramite doplan(PLAN, STEPTIME) e attende l'esito finale (doplandone(ARG) oppure doplanfailed(PLANTODO)).
    • Contesto d'uso ideale: È la soluzione ottimale in contesti dinamici o critici, in cui il software di alto livello deve ispezionare, validare o alterare il percorso prima che i motori vengano azionati (ad esempio per verificare che la traiettoria pianificata non attraversi aree temporaneamente interdette, per stimare costi energetici o per iniettare checkpoint intermedi).
    • Valutazione critica per il progetto: Nessun requisito del committente richiede la modifica o l'ispezione runtime del tragitto. Le tratte tra le postazioni della stiva sono predeterminate e non presentano ostacoli dinamici non cooperativi. L'introduzione di questa coppia di chiamate aggiungerebbe una transizione di stato intermedia e una responsabilità di gestione del payload del piano all'interno di cargorobot, senza portare alcun valore aggiunto tangibile al controllo della missione.
  3. Navigazione a coordinate assolute: moverobot
    • Definizione e Semantica: Rappresenta il livello di astrazione più elevato fornito da RobotSmart26. Con una singola richiesta moverobot(TARGETX, TARGETY, STEPTIME), il chiamante specifica esclusivamente la cella cartesiana di arrivo sulla griglia della stiva e il tempo di calibrazione del passo. Il servizio calcola internamente l'orientamento iniziale, pianifica il percorso ed esegue i passi necessari, restituendo un'unica risposta conclusiva: moverobotdone (o moverobotok(ARG)) in caso di arrivo a destinazione, oppure moverobotfailed(PLANDONE, PLANTODO) in caso di ostacolo imprevisto lungo la rotta.
    • Contesto d'uso ideale: È indicato per scenari di navigazione deterministica all'interno di ambienti a griglia completamente noti in cui il chiamante necessita di delegare per intero la cinematica e il calcolo del percorso al controller del robot.
    • Valutazione critica per il progetto: È l'approccio che minimizza l'abstraction gap. Permette a cargorobot di esprimere la missione ad alto livello secondo la semantica del dominio applicativo ("raggiungi l'IOPort", "raggiungi lo slot 5", "raggiungi lo slot riservato", "torna in HOME") senza dover gestire strutture dati relative al cammino. Inoltre, preserva la manutenibilità del codice applicativo confinando la logica di movimento all'interno del servizio preposto.
Primitiva / Livello Input / Output Vantaggi Svantaggi rispetto al caso d'uso Decisione
step / move step(TIME) → stepdone / stepfailed

Reazione ai Fallimenti di Movimento

Se RobotSmart26 risponde con moverobotfailed(PLANDONE, PLANTODO) (es. percorso ostruito o guasto simulato), cargorobot interrompe la missione, entra in uno stato di sicurezza (halted) e notifica cargoservice tramite il dispatch transportFailed. La decisione su come gestire il sistema (annullamento della prenotazione o stato di allarme) rimane in capo all'orchestratore.

Modellazione del Marker (Slot 5)

Il testo del problema descrive il marker come un dispositivo situato nello slot 5 per l'etichettatura barcode temporanea. Nell'analisi del problema emergono due opzioni:

  1. Attore QActor separato (marker): Riceve la notifica di container depositato, calcola il tempo di etichettatura ed emette un dispatch di avvenuta marcatura.
  2. Attesa gestita all'interno della sequenza di cargorobot: La marcatura è un'operazione atomica che blocca il robot in slot5 per un tempo prefissato prima che possa prelevare nuovamente il container verso lo slot di destinazione.
Per evitare la proliferazione di attori passivi, si valuta di modellare la permanenza in slot5 nello stato atSlot5 tramite una transizione temporizzata esplicita (whenTime 3000), che simula il completamento dell'attività di marcatura prima della ripartenza verso lo slot finale.

Gestione degli Slot e Modellazione della Stiva (Hold)

Nel corso dello Sprint 1, la classe Hold si limitava a tenere traccia della disponibilità numerica e dello stato astratto degli alloggiamenti (FREE, RESERVED, OCCUPIED) per abilitare le risposte di accettazione o rifiuto delle richieste. Con l'introduzione della movimentazione autonoma del DDR nello Sprint 2, la stiva deve arricchirsi di una rappresentazione spaziale conforme al sistema di riferimento a coordinate cartesiane richiesto da RobotSmart26.

Separazione tra Topologia Immutabile e Stato Dinamico

La gestione delle informazioni all'interno della stiva presenta due componenti con requisiti di mutabilità opposti:

  1. Layout Fisso e Topologia Immutabile: Comprende le coordinate cartesiane (X, Y) delle posizioni operative fisse della stiva, definite in base alla griglia euclidea introdotta nello Sprint 0:
    • HOME: punto di stazionamento iniziale e finale del robot;
    • IOPort: area di carico e accesso antistante la porta;
    • slot5: area per la sosta temporanea e la marcatura barcode;
    • slot1..4: coordinate di deposito dei quattro alloggiamenti definitivi. Questi valori sono costanti di progetto e non cambiano mai nel corso dell'esecuzione. Possono quindi essere letti in totale sicurezza e concorrenza da più attori senza incorrere in condizioni di corsa (race condition).
  2. Stato Dinamico di Occupazione: Riguarda la mutabilità dello stato dei singoli alloggiamenti (FREE, RESERVED, OCCUPIED) e l'identificativo dell'eventuale slot riservato correntemente in attesa di deposito. Poiché questo stato è mutevole, deve risiedere esclusivamente all'interno dell'istanza Hold gestita dall'attore orchestratore cargoservice.
Questa distinzione architetturale consente a cargorobot di istanziare una copia locale di sola lettura di Hold, interrogandola unicamente per ricavare le coordinate dei punti di interesse (getHomeX()/getHomeY(), getIOPortX()/getIOPortY(), getMarkerX()/getMarkerY()), senza poter alterare indebitamente lo stato delle riserve della stiva.

Interfaccia IHold

L'entità Hold incapsula la mappa della stiva esponendo metodi sincroni ad alto livello:

Metodo Chiamante Scopo e Responsabilità
reserveNextFreeSlot() cargoservice Ricerca sequenziale del primo slot con stato FREE. Se trovato, lo marca provvisoriamente come RESERVED e ne restituisce l'indice (1..4); se tutti sono impegnati o la stiva è piena, restituisce NO_SLOT_AVAILABLE (= -1).
releaseSlot(slotId) cargoservice Chiamato in caso di timeout dei 30s o a seguito di un fallimento del movimento (transportFailed): ripristina lo stato dello slot prenotato a FREE.
setSlotOccupied(slotId) cargoservice Invocato alla ricezione di transportDone: commuta in modo definitivo lo stato dello slot da RESERVED a OCCUPIED.
getEntranceX(slotId) /
getEntranceY(slotId) 		cargoservice Restituisce la coppia di coordinate cartesiane associate all'ingresso dell'alloggiamento target, passate come argomenti nella richiesta transportContainer.
getHoldStateString() cargoservice Serializza lo stato corrente dei 4 slot in una stringa compatta (es. [RESERVED, FREE, FREE, FREE]) per l'aggiornamento a display tramite l'IOPort.
isFull() cargoservice Controlla se la stiva è piena, ovvero se non c'è nessuno slot in stato FREE.

Project

L'attore cargorobot

L'attore implementa la seguente sequenza:

  1. Movimento da HOME a IOPort;
  2. Movimento da IOPort a slot5 (con sosta di marcatura barcode);
  3. Movimento da slot5 allo slot finale riservato;
  4. Rientro in HOME e chiusura della missione.

        whenTime 30000            -> moveTimeout
        whenReply moverobotdone   -> marking
        whenReply moverobotfailed -> legFailed
        
    State marking {
        println("$name | marker working...") color blue
    }
    Transition t3
        whenTime 5000 -> moveFinalSlot

    // --- 3. slot5 -> slot finale ---
    State moveFinalSlot {
        println("$name | moving to final slot ($X, $Y)") color blue
        request robotsmart -m moverobot : moverobot($X, $Y, $StepTime)
    }
    Transition t4
        whenTime 30000            -> moveTimeout
        whenReply moverobotdone   -> depositContainer
        whenReply moverobotfailed -> legFailed
        
    State depositContainer {
        println("$name | depositing container...") color blue
        delay 2000 
    }
    Goto startHoming
        
    // --- Gestione fallimento di una tappa ---
    State legFailed {
        onMsg (moverobotfailed : moverobotfailed(PLANDONE, PLANTODO)) {
            println("$name | tappa fallita! PLANDONE=${payloadArg(0)} PLANTODO=${payloadArg(1)}") color red
        }
        [# Failed = true #]
    }
    Goto startHoming

    State moveTimeout {
        println("$name | nessuna risposta da robotsmart entro 30s") color red
        [# Failed = true #]
    }
    Goto finishKo

    // --- 4. Rientro in HOME ---
    State startHoming {
        [# HomeAttempts = 0 #]
    }
    Goto goHome

    State goHome {
    	[#
    		HomeAttempts++
    		var XHOME = h.getHomeX()
    		var YHOME = h.getHomeY()
    	#]
        println("$name | going back home (tentativo $HomeAttempts di $MaxHomeAttempts)") color blue
        request robotsmart -m moverobot : moverobot($XHOME, $YHOME, $StepTime)
    }
    Transition t5
        whenTime 30000            -> moveTimeout
        whenReply moverobotdone   -> tuneHome
        whenReply moverobotfailed -> homeMoveFailed
        
    State homeMoveFailed {
        onMsg (moverobotfailed : moverobotfailed(PLANDONE, PLANTODO)) {
            [#
                val Todo = payloadArg(1).filter { c -> c.isLetter() }
                NearHome = (Todo == "w" || Todo == "")
            #]
            println("$name | rientro in HOME fallito: PLANDONE=${payloadArg(0)} PLANTODO=${payloadArg(1)} -> quasi a casa: $NearHome") color red
        }
    }
    Goto tuneHome if [# NearHome #] else retryHome

    State retryHome {
        println("$name | lontano da HOME, ritento il rientro") color magenta
    }
    Goto goHome if [# HomeAttempts < MaxHomeAttempts #] else homeGiveUp

    State homeGiveUp {
        println("$name | impossibile rientrare in HOME dopo $MaxHomeAttempts tentativi") color red
        [# Failed = true #]
    }
    Goto finishKo

    // --- Allineamento in HOME ---
    State tuneHome {
        println("$name | tuning at home...") color blue
        request robotsmart -m tuneAtHome : tuneAtHome(end)
    }
    Transition t6
        whenTime 20000     -> tuneTimeout
        whenReply tuneDone -> endHoming
        
    State tuneTimeout {
        println("$name | tune NON terminato entro 20s") color red
        [# Failed = true #]
    }
    Goto finishKo

    State endHoming {
        println("$name | tune completato, robot riallineato in HOME") color blue
        forward robotsmart -m setrobotstate : setpos(0,0,down)
        delay 300
    }
    Goto finishKo if [# Failed #] else finishOk

    State finishOk {
        println("$name | trasporto finito con successo") color blue
        replyTo transportContainer with transportDone : transportDone($Slot)
    }
    Goto idle

    State finishKo {
        println("$name | trasporto fallito ($FailCause)") color red
        replyTo transportContainer with transportFailed : transportFailed($FailCause)
    }
    Goto idle
}

package cargoservice;

import cargoservice.IHold.SlotState;

public class Hold implements IHold{

    private final SlotState[] mainSlots = new SlotState[NUM_MAIN_SLOTS];
    /*
     * INGRESSI SCELTI:
     * - slot1 = (0,2)
     * - slot2 = (0,3)
     * - slot3 = (2,2)
     * - slot4 = (2,3)
     */
    private final int[] slotEntranceX = {0,0,2,2};
    private final int[] slotEntranceY = {2,3,2,3};
    private final int[] homePos = {0,0};
    private final int[] ioportPos = {4,0};
    private final int[] markerPos = {2,5};
    private static final int X = 0;
    private static final int Y = 1;    

    public Hold() {
        for (int i = 0; i < NUM_MAIN_SLOTS; i++) {
            mainSlots[i] = SlotState.FREE;
        }
    }

    @Override
    public synchronized int reserveNextFreeSlot() {
        for (int i = 0; i < NUM_MAIN_SLOTS; i++) {
            if (mainSlots[i] == SlotState.FREE) {
                mainSlots[i] = SlotState.RESERVED;
                return i + 1;
            }
        }
        return NO_SLOT_AVAILABLE;
    }

    @Override
    public synchronized void setSlotOccupied(int slotNumber) {
        if (isValidSlot(slotNumber)) {
            mainSlots[slotNumber - 1] = SlotState.OCCUPIED;
        }
    }

    @Override
    public synchronized void releaseSlot(int slotNumber) {
        if (isValidSlot(slotNumber)) {
            mainSlots[slotNumber - 1] = SlotState.FREE;
        }
    }

    @Override
    public synchronized boolean isFull() {
        for (int i = 0; i < NUM_MAIN_SLOTS; i++) {
            if (mainSlots[i] == SlotState.FREE) {
                return false;
            }
        }
        return true;
    }

    private boolean isValidSlot(int slotNumber) {
        return slotNumber >= 1 && slotNumber <= NUM_MAIN_SLOTS;
    }
    
    @Override
    public synchronized int getEntranceX(int slotNumber) {
    	if (isValidSlot(slotNumber)) {
    		return slotEntranceX[slotNumber-1];
        }
        return -1;
    }
    
    @Override
    public synchronized int getEntranceY(int slotNumber) {
    	if (isValidSlot(slotNumber)) {
    		return slotEntranceY[slotNumber-1];
        }
        return -1;
    }
    
    @Override
    public synchronized String getHoldStateString() {
        StringBuilder sb = new StringBuilder("[");
        for (int i = 0; i < NUM_MAIN_SLOTS; i++) {
            sb.append(mainSlots[i]);
            if (i < NUM_MAIN_SLOTS - 1) {
                sb.append(", ");
            }
        }
        sb.append("]");
        return sb.toString(); // Restituisce es: "[RESERVED, FREE, FREE, FREE]"
    }
    
    @Override
    public SlotState getSlotState(int slotNumber) {
    	if (isValidSlot(slotNumber)) {
    		return mainSlots[slotNumber-1];
        }
        return null;
    }

	@Override
	public synchronized int getHomeX() {
		return homePos[X];
	}

	@Override
	public synchronized int getHomeY() {
		return homePos[Y];
	}

	@Override
	public synchronized int getIOPortX() {
		return ioportPos[X];
	}

	@Override
	public synchronized int getIOPortY() {
		return ioportPos[Y];
	}

	@Override
	public synchronized int getMarkerX() {
		return markerPos[X];
	}

	@Override
	public synchronized int getMarkerY() {
		return markerPos[Y];
	}
}
