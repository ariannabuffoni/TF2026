TF26 - Sprint3

Goal Sprint3: Progettare e realizzare il sottosistema telemetrico sonar e l'attuatore led, integrando il firmware su microcontrollore o nodo dedicato. Completare la gestione delle anomalie telemetriche con transizione nello stato Out of service a display e gestire la segnalazione luminosa nelle diverse fasi operative.

Introduction

A Maritime Cargo shipping company (from now on, simply company) intends to automate the operations of load of containers in the ship’s cargo hold (or simply hold). To this end, the company plans to employ a Differential Drive Robot (from now, called cargorobot).

The hold is a rectangular, flat area with an Input/Output port (IOPort). The area provides 4 slots to store the containers and a slot named slot5.

In the picture above:

  • The slots1-4 depict the hold areas reserved to store one container each,
  • The slot5 depicts an area, where the cargorobot must temporarily store a container, before to place it in one of the slots1-4. During temporary storage, a ‘marker’ device labels the container with an identification barcode and signals when this marking activity is completed.
  • The IOPort is a device with a pushbutton and a display. The pushbutton is pressed by the customer in order to to send a request to load a container on the cargo. The display is used to show the answer to the request and to show the current state of the hold.
  • The sensor associated to the IOPort is a device (a sonar) used to detect the presence of a container, when it measures a distance D, such that D < DFREE/2, during a reasonable time (e.g. 3 secs).

Requirements

The company asks us to build service named cargoservice that should work as follows.

The cargoservice is able to receive a request to load a container sent by some customer by using the pushbutton of the IOPort.

  • It sends the answer retrylater, if the IOPort is currently occupied by a container or if the system is Out of service
  • It rejects the request when the hold is already full, i.e. the slots1-4 are already occupied.
  • Otherwise, it considers the system as engaged, detects a free slot and returns as answer the name of such a reserved slot. While engaged, the system must blink a Led.

When the request to load is accepted, the customer must move the container in the sensor area within prefixed amount of time (e.g. 30 secs), otherwise the systems becomes disengaged. Then, the cargoservice uses the cargorobot to move the container from the IOPort to the slot5 (for marking the container) and then to the reserved slot.

The service must also show on the display on the IOPort:

  • the current state of the hold
  • the message ‘Service working’, when it is all is going well
  • the message ‘Out of service’ if the sonar sensor measures a distance D > DFREE for at least 3 secs (perhaps a failure of the sonar).

Problem analysis

Il ruolo dell'attore sonar come intermediario tecnologico

Il dispositivo fisico preposto al campionamento dello spazio antistante l'IOPort è un microcontrollore Raspberry PicoW dotato di un sensore a ultrasuoni HC-SR04. Il PicoW esegue un runtime leggero MicroPython e dispone di risorse computazionali e stack di rete limitati: non è in grado di eseguire l'infrastruttura JVM né di istanziare il runtime degli attori QAk. Non è concepibile accoppiare direttamente la logica centrale di cargoservice con le letture grezze del microcontrollore:

  • Il microcontrollore produce misurazioni scalari istantanee rumorose (distanza in centimetri).
  • cargoservice deve invece reagire unicamente a condizioni logiche di dominio stabili e validate nel tempo ("container posizionato con successo", "anomalia hardware rilevata").

Si conferma la scelta architetturale delineata nello Sprint 0: introdurre un attore software dedicato, sonar (QActor in ctxcargoservice), avente il ruolo di Adapter tecnologico e filtro semantico. L'attore sonar aggrega il flusso di campionamento grezzo proveniente dal PicoW, applica la logica dei filtri temporali e notifica a cargoservice, cargorobot e ioport solo le transizioni di stato confermate.

Canale di comunicazione tra Raspberry PicoW e l'Attore sonar

Il microcontrollore PicoW deve comunicare la distanza D all'attore sonar e ricevere dal sistema il comando di attivazione del LED. Analizziamo le alternative per questo canale eterogeneo:

Alternativa Caratteristiche e Vantaggi Limiti e Criticità Valutazione
Seriale su USB/UART Nessun componente middleware aggiuntivo; comunicazione punto-a-punto a bassissima latenza. Impone un vincolo fisico: il microcontrollore deve essere collegato via cavo USB alla stessa macchina che ospita il processo JVM di sonar. Scartata: vanifica la natura distribuita e autonoma del nodo sensore.
Socket TCP grezzo Connessione diretta via WiFi tra PicoW e porta TCP dedicata su JVM. Richiede la gestione manuale del server socket su Java/Kotlin, la riconnessione automatica in caso di drop del WiFi e la definizione di un protocollo applicativo custom. Scartata: eccessivo codice infrastrutturale a basso livello.
Broker MQTT (WiFi) Disaccoppiamento spaziale completo: il PicoW trasmette via WiFi a un broker MQTT. Supporta nativamente la bidirezionalità tramite topic distinti (cargoservice/sonar/distance e cargoservice/sonar/led). Richiede la presenza di un broker MQTT (es. Eclipse Mosquitto) nella rete locale. Adottata: garantisce flessibilità di rete e massima interoperabilità senza vincoli di cablaggio.

Integrazione di MQTT nel Modello QAk: Nativo vs Adapter

Scelto MQTT come canale di trasporto, si presentano due modalità per far interagire il broker con l'attore sonar:

  1. Adapter Java dedicato (approccio simile a IOPortWsAdapter): Una classe POJO apre la connessione Paho MQTT, riceve i messaggi e inietta dispatch nell'attore tramite sendMsgToMyself. Seppur efficace per WebSocket, questa soluzione introduce codice boilerplate ridondante quando il framework offre alternative dichiarative.
  2. Supporto Nativo QAk a livello di System (Scelta Adottata): Il metamodello QAk permette di dichiarare a livello di sistema un broker MQTT con la direttiva: 
    mqttBroker "IP_BROKER" port 1883 eventTopic "cargoservice/sonar/distance"
    In questo modo, qualsiasi evento pubblicato su tale topic nel formato standard msg(...) viene intercettato direttamente dal runtime QAk e consegnato come Event sonarreading : sonarreading(D) a chiunque possieda una transizione whenEvent sonarreading.
In direzione inversa (verso il LED del PicoW): Il runtime non dispone di una dichiarazione implicita per topic in uscita; l'invio del comando verso il PicoW viene quindi gestito in modo pulito invocando l'oggetto di runtime mqtt.publish(...) direttamente dall'attore sonar.

Frequenza di Campionamento e Validazione Temporale delle Soglie

I requisiti impongono il rispetto di due soglie geometrico-temporali:

  1. Rilevamento Container: D < DFREE/2 mantenuto per un intervallo temporale continuo di almeno 3 secondi.
  2. Allarme Guasto Sonar: D > DFREE mantenuto per un intervallo continuo di almeno 3 secondi.

Scelta della Frequenza di Pubblicazione del PicoW

Una frequenza elevata (es. 10 Hz / 100 ms) genererebbe un traffico di rete inutile sul broker MQTT e introdurrebbe rumore sui micro-rimbalzi degli ultrasuoni, senza apportare vantaggi significativi a fronte di una finestra di filtro ampia di 3 secondi.
Una frequenza di 1 lettura al secondo (1 Hz) garantisce circa 3 campioni consecutivi all'interno della finestra di convalida, sufficienti a scongiurare falsi positivi (dovuti a passaggi transitori di operatori o errori isolati di eco) preservando la reattività del sistema e riducendo al minimo il sovraccarico di rete.

Responsabilità del Monitoraggio Temporale

Il Raspberry PicoW si limita a campionare la distanza e trasmettere il dato numerico grezzo. È l'attore sonar a detenere la macchina a stati temporale:

  • Registra il timestamp del primo superamento di soglia (Tstart).
  • Solo quando le letture persistono oltre la soglia per un intervallo (Tcurrent - Tstart) ≥ 3000 ms, l'attore emette i messaggi di conferma verso il sistema centrale (sonarcontainer per il carico, sonarfault per il guasto).
  • Al contrario, l'uscita da una condizione (es. container rimosso o distanza rientrata nei limiti normali) viene notificata istantaneamente (setOccupied(false) o sonarrestored) senza necessità di ritardi di conferma.

Reazione di cargorobot al guasto del Sonar durante il movimento

Il committente specifica che l'anomalia telemetrica (D > DFREE persistente per più di 3 secondi) pone l'intero sistema in stato Out of service. Sorge una questione critica su come debba comportarsi cargorobot qualora tale guasto si manifesti mentre il robot è in movimento lungo una delle quattro tratte previste (verso IOPort, verso slot5, verso lo slot riservato, verso HOME):

  • Opzione 1 (Arresto e annullamento della missione): Il robot abortisce il trasporto, rilascia lo slot e tenta di rientrare in HOME o dichiara fallimento immediato. Questa scelta è rischiosa e scorretta: se il robot trasporta fisicamente un container ed è a metà strada, non può resettare lo stato della stiva senza causare inconsistenze fisiche tra carico e allocazione dello slot.
  • Opzione 2 (Sospensione della tratta con evento alarm e successiva ripresa): Quando l'attore sonar rileva il guasto, inoltra un dispatch sonarfault sia a cargoservice sia a cargorobot.
    1. cargorobot, sensibile a sonarfault in ciascuno dei suoi stati di attesa movimento, emette immediatamente l'evento alarm: alarm(sonarfault) verso RobotSmart26, che provvede a fermare istantaneamente il robot.
    2. cargorobot memorizza la tratta attiva (Leg: toIOPort, toSlot5, toReserved, toHome) e le coordinate di destinazione correnti.
    3. All'eventuale ricezione di sonarrestored (distanza tornata nei valori ammissibili), cargorobot reinvia la richiesta moverobot verso il target interrotto, riprendendo la missione senza perdere lo stato di avanzamento.
Si adotta l'Opzione 2 in quanto rispetta i requisiti di sicurezza industriale e previene disallineamenti di stato.

Architettura dei Contesti: Context Dedicato per sonar vs Context Condiviso

L'introduzione del Raspberry PicoW rappresenta l'aggiunta di un nodo hardware fisico separato nella rete. Ci si domanda se tale separazione imponga la creazione di un ulteriore contesto QAk (ctxsonar) isolato.

  • Analisi dei confini di rete: La vera disomogeneità tecnologica risiede tra il microcontrollore PicoW (ambiente MicroPython) e la JVM. Questo salto di rete e di stack è già interamente assorbito dal broker MQTT.
  • Valutazione del contesto QAk: Spostare l'attore sonar in un processo/contesto QAk separato (ctxsonar) costringerebbe a dichiarare attori remoti (ExternalQActor) e a introdurre socket TCP aggiuntivi tra sonar e cargoservice/cargorobot, senza alcun beneficio architetturale.
  • Decisione: L'attore sonar viene collocato all'interno del contesto ctxcargoservice (porta 8120), condividendo il processo JVM con gli altri attori dell'applicazione (cargoservice, cargorobot, ioport). L'unico vero contesto esterno rimane ctxrobotsmart (porta 8020), in quanto servizio preesistente fornito dal committente.

Gestione dell'Attuatore LED su Microcontrollore

Il LED deve riflettere fedelmente le transizioni operative stabilite: spento in idle, lampeggiante in engaged e durante la movimentazione, rosso fisso o spento in Out of service.

  • Il firmware MicroPython sul PicoW opera su un singolo thread di esecuzione e non può ricorrere a delay bloccanti (time.sleep) che impedirebbero il campionamento continuo del sensore a ultrasuoni.
  • Il comando di accensione/spegnimento lampeggio (blinkLed(true) / blinkLed(false)) viene inviato da cargoservice via dispatch verso sonar, che lo pubblica sul topic MQTT cargoservice/sonar/led.
  • Il PicoW aggiorna un flag booleano nel callback di ricezione MQTT e alterna lo stato del pin GPIO del LED in modo non bloccante all'interno del ciclo principale di lettura.

L'attore sonar

L'attore sonar gestisce il filtraggio delle soglie telemetriche mantenendo i timestamp di sistema. Trasmette gli aggiornamenti di stato solo se le letture persistono oltre la finestra di convalida di 3000 ms: 

QActor sonar context ctxcargoservice {
    [#
        val DFREE = 30.0
        var Dist = 0.0
        var Occupied = false
        var Faulted = false
        var T0Container = 0L
        var T0Fault = 0L
        val WINDOW = 3000L
    #]

    State idle initial {
        println("$name | pronto in ascolto degli eventi sonar via MQTT") color blue
    }
    Transition t0 
        whenEvent sonarreading -> onReading
        whenMsg   blinkLed     -> onBlink

    State onReading {
        onMsg(sonarreading : sonarreading(D)) {
            [#
                Dist = payloadArg(0).toDouble()
                val now = System.currentTimeMillis()
            #]

            // --- Logica Finestra Convalida Container (D < DFREE/2 per >= 3s) ---
            if [# Dist < (DFREE / 2.0) #] {
                [# if (T0Container == 0L) T0Container = now #]
                if [# !Occupied && (now - T0Container) >= WINDOW #] {
                    [# Occupied = true #]
                    println("$name | Container confermato a D=$Dist cm per >= 3s") color blue
                    forward cargoservice -m sonarcontainer : sonarcontainer($Dist)
                }
            } else {
                [# T0Container = 0L #]
                if [# Occupied && Dist >= (DFREE / 2.0) #] {
                    [# Occupied = false #]
                    println("$name | Container rimosso dall'area sensore") color blue
                }
            }

            // --- Logica Finestra Convalida Guasto Sonar (D > DFREE per >= 3s) ---
            if [# Dist > DFREE #] {
                [# if (T0Fault == 0L) T0Fault = now #]
                if [# !Faulted && (now - T0Fault) >= WINDOW #] {
                    [# Faulted = true #]
                    println("$name | GUASTO RILEVATO: D=$Dist cm per >= 3s") color red
                    forward cargoservice -m sonarfault : sonarfault(sonarOutOfRange)
                    forward cargorobot   -m sonarfault : sonarfault(sonarOutOfRange)
                }
            } else {
                [# T0Fault = 0L #]
                if [# Faulted #] {
                    [# Faulted = false #]
                    println("$name | Sonar ripristinato entro i parametri normali") color blue
                    forward cargoservice -m sonarrestored : sonarrestored(NONE)
                    forward cargorobot   -m sonarrestored : sonarrestored(NONE)
                }
            }
        }
    }
    Goto idle

    State onBlink {
        onMsg(blinkLed : blinkLed(FLAG)) {
            [#
                val flag = payloadArg(0)
                val ledDispatch = unibo.basicomm23.utils.CommUtils.buildDispatch(
                    name, "blinkLed", "blinkLed($flag)", "picow"
                )
                mqtt.publish("cargoservice/sonar/led", ledDispatch.toString())
            #]
            println("$name | Comando LED ($flag) inoltrato a PicoW via MQTT") color blue
        }
    }
    Goto idle
}

Raffinamento dell'attore cargoservice

Nello Sprint 3, cargoservice sincronizza l'avvio della missione alla ricezione di sonarcontainer e governa lo stato protetto Out of service: 

State engaged {
    println("$name | ENGAGED: attesa rilevamento container dal sonar (max 30s)") color magenta
    forward sonar -m blinkLed : blinkLed(true)
}
Transition tEng 
    whenTime 30000          -> disengagedTimeout
    whenMsg sonarcontainer  -> startTransport
    whenMsg sonarfault      -> engagedOutOfService
    whenRequest loadrequest -> rejectBusyRequest

State startTransport {
    println("$name | Container rilevato fisicamente: incarico cargorobot") color magenta
    [#
        val targetX = h.getSlotX(CurrentReservedSlot)
        val targetY = h.getSlotY(CurrentReservedSlot)
    #]
    request cargorobot -m transportContainer : transportContainer($CurrentReservedSlot, $targetX, $targetY)
}
Transition tTrans 
    whenReply transportDone    -> handleTransportSuccess
    whenReply transportFailed  -> handleTransportFailure
    whenMsg   sonarfault       -> transportOutOfService
    whenMsg   sonarrestored    -> transportRestored
    whenRequest loadrequest    -> rejectBusyRequest

State engagedOutOfService {
    println("$name | GUASTO durante fase engaged: rilascio slot") color red
    [#
        if (CurrentReservedSlot != -1) {
            h.releaseSlot(CurrentReservedSlot)
            CurrentReservedSlot = -1
        }
        val holdStr = h.getHoldStateString()
    #]
    forward sonar  -m blinkLed : blinkLed(false)
    forward ioport -m updateWorkingState : updateWorkingState("OUT_OF_SERVICE")
    forward ioport -m updateHoldDisplay : updateHoldDisplay("OUT_OF_SERVICE", $holdStr, "Guasto sonar")
}
Goto outOfServiceWait

State outOfServiceWait {
    println("$name | Sistema BLOCCATO in Out of service") color red
}
Transition tOos 
    whenMsg sonarrestored   -> onServiceRestored
    whenRequest loadrequest -> rejectOutOfService

State onServiceRestored {
    println("$name | Sonar ripristinato: ritorno in IDLE") color magenta
    [# val holdStr = h.getHoldStateString() #]
    forward ioport -m updateWorkingState : updateWorkingState("WORKING")
    forward ioport -m updateHoldDisplay : updateHoldDisplay("IDLE", $holdStr, "Service working")
}
Goto idle

Raffinamento dell'attore cargorobot: Sospensione e Ripresa Tratta

Per gestire il guasto telemetrico durante la movimentazione, cargorobot memorizza la tratta attiva (Leg) e le coordinate correnti di destinazione. Se sopraggiunge sonarfault, blocca RobotSmart26 con alarm e attende sonarrestored per riprendere la rotta interrotta: 

QActor cargorobot context ctxcargoservice {
    [#
        var TargetSlot = -1
        var TargetX = -1
        var TargetY = -1
        val StepTime = 345
        var PendingTX = -1
        var PendingTY = -1
        var Leg = "" // "toIOPort" | "toSlot5" | "toReserved" | "toHome"
    #]
    withobj hold using "cargoservice.Hold()"

    State idle initial {
        println("$name | pronto in IDLE") color blue
    }
    Transition t0 whenRequest transportContainer -> prepareMoveToIOPort

    State prepareMoveToIOPort {
        onMsg(transportContainer : transportContainer(SLOT, TARGETX, TARGETY)) {
            [#
                TargetSlot = payloadArg(0).toInt()
                TargetX    = payloadArg(1).toInt()
                TargetY    = payloadArg(2).toInt()
                val pos = hold.getIOPortPosition()
                PendingTX = pos.x
                PendingTY = pos.y
                Leg = "toIOPort"
            #]
            request robotsmart -m moverobot : moverobot($PendingTX, $PendingTY, $StepTime)
        }
    }
    Transition t1 
        whenReply moverobotdone   -> atIOPort
        whenReply moverobotfailed -> handleMoveFailed
        whenMsg   sonarfault      -> onSonarFaultDuringMove

    State atIOPort {
        println("$name | A IOPort, prelievo carico") color blue
    }
    Transition t2 whenTime 1500 -> prepareMoveToSlot5

    State prepareMoveToSlot5 {
        [#
            val pos = hold.getSlot5Position()
            PendingTX = pos.x
            PendingTY = pos.y
            Leg = "toSlot5"
        #]
        request robotsmart -m moverobot : moverobot($PendingTX, $PendingTY, $StepTime)
    }
    Transition t3 
        whenReply moverobotdone   -> atSlot5
        whenReply moverobotfailed -> handleMoveFailed
        whenMsg   sonarfault      -> onSonarFaultDuringMove

    State atSlot5 {
        println("$name | A Slot5: marcatura barcode...") color blue
    }
    Transition t4 whenTime 3000 -> prepareMoveToReserved

    State prepareMoveToReserved {
        [#
            PendingTX = TargetX
            PendingTY = TargetY
            Leg = "toReserved"
        #]
        request robotsmart -m moverobot : moverobot($PendingTX, $PendingTY, $StepTime)
    }
    Transition t5 
        whenReply moverobotdone   -> atReservedSlot
        whenReply moverobotfailed -> handleMoveFailed
        whenMsg   sonarfault      -> onSonarFaultDuringMove

    State atReservedSlot {
        println("$name | Container depositato nello slot $TargetSlot") color blue
    }
    Transition t6 whenTime 1500 -> prepareReturnHome

    State prepareReturnHome {
        [#
            val pos = hold.getHomePosition()
            PendingTX = pos.x
            PendingTY = pos.y
            Leg = "toHome"
        #]
        request robotsmart -m moverobot : moverobot($PendingTX, $PendingTY, $StepTime)
    }
    Transition t7 
        whenReply moverobotdone   -> transportCompleted
        whenReply moverobotfailed -> handleMoveFailed
        whenMsg   sonarfault      -> onSonarFaultDuringMove

    // --- Gestione Guasto e Sospensione Tratta ---
    State onSonarFaultDuringMove {
        println("$name | Guasto sonar durante tratta $Leg: ARRESTO ROBOT!") color red
        emit alarm : alarm(sonarfault)
    }
    Transition tHalt whenMsg sonarrestored -> resumeNavigation

    State resumeNavigation {
        println("$name | Sonar ripristinato: ripresa tratta $Leg verso ($PendingTX, $PendingTY)") color yellow
        request robotsmart -m moverobot : moverobot($PendingTX, $PendingTY, $StepTime)
    }
    Transition tResume 
        whenReply moverobotdone   -> evaluateResumedLeg
        whenReply moverobotfailed -> handleMoveFailed

    State evaluateResumedLeg {
        // Rientro nello stato operativo corrispondente alla tratta appena completata
        Goto atIOPort       if [# Leg == "toIOPort" #]   else checkResumedSlot5
    }
    State checkResumedSlot5 {
        Goto atSlot5        if [# Leg == "toSlot5" #]    else checkResumedReserved
    }
    State checkResumedReserved {
        Goto atReservedSlot if [# Leg == "toReserved" #] else transportCompleted
    }

    State transportCompleted {
        println("$name | Trasporto concluso regolarmente in HOME") color blue
        replyTo transportContainer with transportDone : transportDone($TargetSlot)
        [# TargetSlot = -1 #]
    }
    Goto idle

    State handleMoveFailed {
        println("$name | Fallimento irrecuperabile del movimento su RobotSmart26") color red
        replyTo transportContainer with transportFailed : transportFailed(robotStuck)
        [# TargetSlot = -1 #]
    }
    Goto idle
}

Firmware MicroPython su Raspberry PicoW (sonarMqtt.py)

Il firmware rispetta il campionamento a cadenza di circa 1 secondo. Riceve i comandi di controllo del LED senza ricorrere a cicli bloccanti che ostacolerebbero il sensore: 

import time
import machine
from umqtt_simple import MQTTClient
import secrets

# Pinout hardware su Raspberry PicoW
TRIG_PIN = 16
ECHO_PIN = 17
LED_PIN = 15

trigger = machine.Pin(TRIG_PIN, machine.Pin.OUT)
echo = machine.Pin(ECHO_PIN, machine.Pin.IN)
led = machine.Pin(LED_PIN, machine.Pin.OUT)

TOPIC_DISTANCE = b"cargoservice/sonar/distance"
TOPIC_LED = b"cargoservice/sonar/led"

blink_active = False

def on_message(topic, msg):
    global blink_active
    payload = msg.decode()
    if "blinkLed(true)" in payload:
        blink_active = True
    elif "blinkLed(false)" in payload:
        blink_active = False
        led.value(0)

def measure_distance():
    trigger.low()
    time.sleep_us(2)
    trigger.high()
    time.sleep_us(10)
    trigger.low()
    
    timeout = 30000
    start = time.ticks_us()
    while echo.value() == 0:
        if time.ticks_diff(time.ticks_us(), start) > timeout:
            return None
            
    signal_off = time.ticks_us()
    while echo.value() == 1:
        if time.ticks_diff(time.ticks_us(), signal_off) > timeout:
            return None
            
    signal_on = time.ticks_us()
    time_passed = time.ticks_diff(signal_on, signal_off)
    # Velocità del suono: 343 m/s -> 0.0343 cm/us
    distance = (time_passed * 0.0343) / 2.0
    return distance

# Connessione WiFi e Broker MQTT
def setup_mqtt():
    client = MQTTClient(
        client_id="sonarpico",
        server=secrets.MQTT_BROKER_IP,
        port=secrets.MQTT_PORT
    )
    client.set_callback(on_message)
    client.connect()
    client.subscribe(TOPIC_LED)
    return client

client = setup_mqtt()

# Ciclo principale di campionamento (cadenza ~1s)
while True:
    try:
        client.check_msg()
        if blink_active:
            led.toggle()
            time.sleep(0.3)
            
        d = measure_distance()
        if d is not None:
            # Formattazione nel formato evento nativo IApplMessage di QAk
            event_payload = "msg(sonarreading,event,picow,none,sonarreading(%d),0)" % round(d)
            client.publish(TOPIC_DISTANCE, event_payload.encode())
            
        time.sleep(1.0)
    except Exception as e:
        print("Errore nel loop del sensore:", e)
        time.sleep(1.0)

Deployment

Il deployment dello Sprint 3 concretizza l'architettura distribuita finale del sistema. Il prototipo completo è composto da tre nodi computazionali distinti (il sistema applicativo QAk su JVM, il simulatore WEnv con RobotSmart26, e il microcontrollore fisico Raspberry PicoW), coordinati attraverso il broker MQTT e la rete locale.
